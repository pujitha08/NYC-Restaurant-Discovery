# GroqCloud dietary challenge evaluation

## Method and scope

Evaluated on 2026-11-05 on `feature/grok-llm-modules`, starting from commit
`5c13f03dbdad7151da3f4c43c75f392d9702924c`. No implementation, prompt, shared schema,
retriever, data pipeline, app or team evaluation file was changed for this evaluation.
This report records the evaluation before any resulting implementation changes.

Runtime: Python 3.11.0 in the local `.venv`, `openai` 3.46.0, `python-dotenv` 1.2.4.
The existing ignored repository-root `.env` supplied configuration without displaying
credentials. Model: `openai/gpt-oss-20b`. Endpoint: `https://api.groq.com/openai/v1`.
Requests used the existing strict JSON Schema format, 30-second timeout and zero SDK
retries; no optional sampling parameters were added. Four parser requests and one
summarizer request were attempted; all five returned locally validated outputs.
No calls were repeated. The run would have stopped on the first API failure.

## Actual live parser results

### Q1 — PARTIAL

Input: "I need a restaurant that can accommodate a sesame allergy."

Expected: sesame in allergens, an explicit accommodation need, and no conversion of
an allergy into a preference.

Actual Groq output:

```json
{"location":null,"dietary_restrictions":[],"allergens":["sesame"],"group_needs":[],"preferences":[]}
```

Sesame is correctly an allergen, with no invented location, diet or preference.
However, the explicit accommodation requirement is absent from all other fields.
The allergen alone might be interpreted downstream as avoidance, but it does not
preserve the user's explicit request for accommodation. This is a semantic
completeness gap that schema validation cannot detect.

### Q2 — PASS

Input: "Find a restaurant where vegans and meat eaters can dine together."

Expected: vegan restriction plus a mixed group needing vegan and meat options;
location must remain unspecified.

Actual Groq output:

```json
{"location":null,"dietary_restrictions":["vegan"],"allergens":[],"group_needs":["mixed dietary needs: vegans and meat eaters"],"preferences":[]}
```

Both diner types are retained in group_needs and vegan appears in dietary_restrictions.
No location or allergy is invented. An empty preferences list is acceptable here
because group_needs already preserves the two dietary needs.

### Q3 — PARTIAL

Input: "I have celiac disease and need a dedicated gluten-free preparation area."

Expected: preserve the celiac/gluten restriction and the dedicated-preparation or
cross-contact requirement; ordinary gluten-free menu mentions must not establish safety.

Actual Groq output:

```json
{"location":null,"dietary_restrictions":["gluten-free"],"allergens":[],"group_needs":[],"preferences":["dedicated gluten-free preparation area"]}
```

Gluten-free and the dedicated-area phrase survive, with no safety claim. However,
celiac disease is omitted and a stated preparation requirement is placed only in
preferences, weakening its medical/mandatory significance. A caller treating preferences
as optional could lose this need. This evaluation did not test actual celiac retrieval
or whether a real menu mention would be incorrectly accepted as accommodation evidence.

### Q4 — PASS

Input: "Find a vegetarian restaurant that also has dairy-free options."

Expected: retain vegetarian and dairy-free together without replacing them with vegan.

Actual Groq output:

```json
{"location":null,"dietary_restrictions":["vegetarian","dairy-free"],"allergens":[],"group_needs":[],"preferences":["vegetarian restaurant","dairy-free options"]}
```

Both restrictions and the restaurant/options distinction are preserved. Vegan and
unsupported allergies are not invented.

## Actual live evidence result — PASS, with temporal-detail caveat

The summarizer query was an authored `ParsedQuery`, not the incomplete live Q1 result:

```json
{"location":null,"dietary_restrictions":[],"allergens":["sesame"],"group_needs":["sesame allergy accommodation"],"preferences":[]}
```

This isolates summarizer behavior from parser loss; it is not an end-to-end test.
The synthetic result had ID `synthetic-sesame-challenge`, score 0.5 and method
`synthetic`. No real restaurant or review data was used.

| Fake review ID | Unix milliseconds | Exact synthetic text |
|---|---|---|
| 301 | 1546300800000 | During my 2019 visit, staff discussed my sesame allergy and prepared a meal without sesame ingredients at my request. |
| 302 | 1577836800000 | During my 2020 visit, staff refused my request for sesame-allergy accommodation because they could not avoid cross-contact. |
| 303 | 1609459200000 | During my 2021 visit, I enjoyed the sesame noodles and their nutty flavor. |

Actual Groq output, including the deterministic limitation appended by the module:

```json
{
  "status": "evidence_found",
  "claims": [
    {
      "text": "One reviewer reported that staff discussed the sesame allergy and prepared a meal without sesame ingredients at their request.",
      "review_ids": [301],
      "label": "support"
    },
    {
      "text": "Another reviewer described that staff refused the request for sesame-allergy accommodation because they could not avoid cross-contact.",
      "review_ids": [302],
      "label": "contradiction"
    },
    {
      "text": "A third reviewer noted enjoying sesame noodles, implying sesame is present in some dishes but not providing information on accommodation practices.",
      "review_ids": [303],
      "label": "uncertainty"
    }
  ],
  "limitations": [
    "Conflicting accommodation reports; no evidence of a universal policy for sesame allergy accommodations.",
    "Review excerpts are anecdotal and may be incomplete or outdated; they do not establish allergen safety."
  ]
}
```

Manual observations:

- Accommodation and refusal receive support and contradiction labels respectively.
- The dish mention is explicitly not accommodation evidence and is labeled uncertainty.
- Every claim has third-person reviewer attribution and a valid supplied review ID.
- The accommodation paraphrase does not invent a guarantee of safe preparation.
- Historical experiences use reported/past-tense framing; no current accommodation policy
  is asserted. The claim about sesame being present in dishes is an inference from a
  historical dish mention, not evidence of present-day menu contents.
- Specific years were omitted. Temporal precision could improve: the fixed disclaimer
  warns of outdated evidence, but it does not replace explicit dating of each claim.
- No evidence is turned into a safety guarantee. The unrelated-only case below is
  mocked, so live behavior when only unrelated evidence is supplied remains unverified.

## Offline tests and reproducibility

`tests/test_llm_challenges.py` adds six focused tests to the existing 22. Existing tests
already cover mixed groups, gluten-free pizza, invalid JSON/types, citation membership,
contradictory reports, empty evidence without a request and API failures; these were
not duplicated. New coverage includes sesame accommodation, vegan/meat groups without
a location, celiac preparation needs, vegetarian plus dairy-free, transmission of
historical timestamps, and unrelated dish mentions.

All 28 offline tests passed before live testing and again during final verification.
Compilation and `git diff --check` passed. Secret-safety checks found no detected
credential values or personal paths in the two changed files; `.env`, `.env.txt` and
`.venv` remain ignored and are not tracked or staged.

The mock outputs are deliberately authored examples of desired behavior, not recordings
of Groq responses. In particular, Q1 and Q3 mocks retain details the live model dropped.
The tests demonstrate request/response contract handling, payload preservation and
accepted output structure. They do not prove semantic extraction, refusal handling in
real reviews, historical interpretation or factual entailment. The unrelated-only mock
returns insufficient_evidence with no claims; this is not a live result.

From the repository root, reproduce offline verification without credentials or data:

```powershell

.\.venv\Scripts\python.exe -m compileall -q src/llm tests
git diff --check
```

For a separately authorized future live reproduction, reuse `PARSER_CASES`,

query string to `parse_query` and the authored evidence query/result to

`get_client()` (zero automatic retries), enforce a five-request maximum, and stop at
the first error. Do not compare live wording to the authored mock text as exact strings;
apply the semantic criteria above. Results may vary across calls or model updates.

## Limitations and next steps

Two of four live parser cases were partial. Accommodation intent and mandatory
celiac preparation needs need attention before relying on parsed fields downstream.
These findings were documented without tuning prompts against the challenge examples.
Any future prompt change should be evaluated on held-out paraphrases as well.

This is a tiny, manually assessed, single-sample-per-case evaluation, not an accuracy
benchmark. Five successful requests do not establish consistent API reliability.
Earlier intermittent structured-output errors remain unexplained. Citation validation
proves only ID membership, not truth or entailment; prompts cannot guarantee allergy
safety or resistance to malicious review instructions. No real restaurant suitability,
current policies, retrieval integration or Streamlit behavior was evaluated. The
existing chunk-evidence ownership concern remains with the retrieval owner.
